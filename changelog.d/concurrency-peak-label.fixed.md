- **`board_concurrency_get`/`_set` say why the peak isn't always `max_concurrent × coder_solve_k`.** When `max_concurrent_sessions` is set, a card's solve candidates run one after another, so each card holds `min(coder_solve_k, max_concurrent_sessions)` coder sessions. The `peak_formula` now names that cap, and with `coder_solve` off it says one session per card. The number was already right; the old label made 4 coders with `coder_solve_k` 3 look like a 4 × 1 bug.
