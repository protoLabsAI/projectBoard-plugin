- **Registering a board project makes it a read-only managed project (#452).**
  `board_register_project` and `PUT /projects/{name}` used to write only
  `project_board.projects`, so the lead agent's filesystem tools could not read the checkout
  its coders branch from. They now also add a read-only entry to the host's managed-projects
  registry (ADR 0095 `projects:`): `github` comes from the `origin` remote and
  `default_branch` is the base branch. It goes in the same `HOST.apply_settings` patch,
  shaped like `onboard_project`'s. An entry that already exists is left alone. Unregistering
  removes the entry only if the board added it and it still points at the board's repo.
  The merge runs inside the host's config write lock (the callable `HOST.apply_settings`)
  and refuses to drop any existing entry, so a concurrent `onboard_project` write survives.
  **This raises `min_protoagent_version` to 0.164.0**: the registry write is a locked
  read-modify-write of the host's `projects:` list, and only protoAgent 0.164.0+ runs a
  callable `HOST.apply_settings` patch inside its config write lock (#2743). Older hosts
  are expected to upgrade; there is no unlocked fallback.
- **Board-owned base checkouts are fast-forwarded (#452).** Each health sweep starts a refresh
  pass as its own task, off the tick. The pass fetches every board-owned checkout's base
  concurrently, under one budget. A checkout is board-owned when it is under the onboarding
  root or was registered by the board; any other checkout needs `base_refresh: true` on its
  project. The pass runs `merge --ff-only --no-overwrite-ignore` on the MAIN checkout, but
  only when it is clean, on the base branch, and has nothing the remote lacks. The board never
  resets, stashes, switches branches, or overwrites an ignored local file. Any other checkout
  is left as it is and listed under `stale_base_checkouts` on `GET /status`. The new
  `base_refresh` setting (default on) turns the pass off.
