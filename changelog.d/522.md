- **Board cards in chat (#522).** A status check-in ("what's blocked?", "how's epic #4076?") can now answer with live board cards in the transcript instead of paragraphs. The new `board_show_cards(ids=[], state="", project="", title="")` tool returns a short text summary plus a `board-cards` component. Its props are pointers only: up to 20 card ids, or a state/project query, and a title. The component is a plugin-served frame page (`component/board-cards.html`, public via the manifest's new `public_paths`). Each card shows its state badge, `next_action` or block reason, project and PR link. The page re-reads its cards about every 15 seconds through the console's mediated reads (protoAgent#4143), and immediately on mount and on a re-theme. It pauses while out of view, so a reloaded or replayed answer shows current state with a "refreshed Ns ago" note. Buttons appear only in their state: Unblock / Why?, Re-review, Merge (only when the card is `awaiting_merge` with CI not red), Show coder, Dispatch now. Each one proposes an exact message (`Unblock board card bd-…` etc.) that the operator confirms in the chat's chip. PR links open through the bridge's `openLink`. The new `showing-board-cards` skill tells the agent when to show cards, when not to, and which `board_*` tool answers each button. Two new read-only routes return slim card rows: `GET /cards/<state>` for a state query and `GET /cards` for open work only (no done or cancelled cards). Every listing is capped and carries the pre-cap `total`: done and cancelled to the 50 most recently closed, everything else to the 100 most urgent (priority, then most recently updated). So no read grows with the board; the page and the tool summary say "showing N of TOTAL" when capped. They take no query string, because the host serves declared read paths only, so the frame filters by project itself. On a core without `register_component(..., reads=)` the board records one setup gap (`board_cards`) and the tool answers in text only. `board_list` and `board_get_feature` are unchanged. Every read, send and openLink the page makes echoes the per-mount `nonce` from `protoComponent:init` (protoAgent#4172); a request the host refuses is shown as a refusal. `board_show_cards()` with no arguments shows the whole board's open work (every state but done), the "how's the board?" check-in. A project query reads `GET /cards/<state>/<project>` (`open` for no state), so the server filters by project before it caps. The page follows protoAgent#4172's handshake: it reads `#pair=` from its URL, posts `protoComponent:ready {pair}` once, and treats an init with no nonce (or no `#pair=` and an init without one) as an older core; a slow read is retried with backoff and never marks the core as old. Buttons and proposals appear only for ids of the real `bd-<hash>[.<n>]` shape, and the props validator no longer accepts a trailing newline in an id.
