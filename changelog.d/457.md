- **Publish gates: a card can wait for a release, not just a merge (`waits_for`).**
  `depends_on` releases a dependent when its blocker merges, and a version floor
  (`>0.62.0`) can be met by an unrelated publish, such as a changesets Version PR that was
  already open. Both are too early for a consumer that installs what the blocker
  publishes. A card (feature or task) can now carry
  `waits_for="npm:@protolabsai/ui@contains:protoLabsAI/protoContent@bd-a1"`. It holds
  only once the newest published version is git-tagged at a descendant of card bd-a1's
  merge commit (checked with GitHub compare), and it stays unmet until bd-a1 merges. Other
  kinds: `npm:<pkg>@<range>`, `release:<owner>/<repo>@<tag>`,
  `release:<owner>/<repo>@<package>@<range>` (a bare range is refused on a repo that tags
  per package) and `pr:<owner>/<repo>#<n>`. The loop leaves the card unclaimed until every
  gate holds, and the card says why (`waiting on publish: …`). The wait is never counted
  as a livelock.
  - Checks are cached per spec, shared across cards, and back off on errors.
  - A failed or unreadable check keeps the card held and shows the error. It never stops
    the loop or a listing.
  - `board_check_gates` / `POST /features/{fid}/gates/check` check now.
  - Ranges follow node-semver, including its prerelease rule. Deprecated npm versions
    never count.
  - Specs live in the bead's notes, not in a label, because a real spec is longer than
    beads' 50-character label cap.
  - Private packages read with the new `npm_token` secret.
- **Auto-merge holds while the target repo is cutting a release.** Before merging, the
  loop checks the PR's repo for a `prepare-release*` branch, an open PR from one, an
  active `prepare-release.yml` run, or an untagged `chore: release v*` head commit. If it
  finds one, it holds the merge: the card stays in review reading
  `held: release freeze (<evidence>)`, no merge attempt is spent, and the merge lands on
  the first poll after the release. Per-project `release_freeze` sets the patterns, or
  `false` turns it off, as for a changesets repo like protoContent. A signal the token
  can't read (403) is skipped and shown in the setup status; any other check error holds
  the merge.
