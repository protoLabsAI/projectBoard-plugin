- **When one source issue is split across several cards, only the last slice to publish closes it.** `_inject_source_issue_line` stamped `Fixes #N` on every same-repo PR whose card carried that `source_issue`, so the first merged slice closed the umbrella issue out from under its siblings (nerdsville-site#6 closed by slice PR #39/#40). The PR body now gets `Refs #N` instead whenever ANY other slice of the same issue still has work that is NOT yet captured in a PR — a card that is still being coded (non-terminal, not `in_review`, no `pr_url`). Once every other slice's work is in a PR (`in_review`/`done`, or a `pr_url` present), the next slice to publish keeps `Fixes #N` and closes the issue. The earlier cut counted an `in_review` sibling as "still open", so two slices that reached review at the same time BOTH got `Refs #N` and the issue never closed after all of them merged; keying off "work captured in a PR" instead of "non-terminal" fixes that. A store read error while scanning siblings fails SAFE to `Refs` — an uncertain read never closes an issue early. In `refs_only` mode a `Fixes/Closes #N` already present in the generated body is rewritten to `Refs #N` (not left in place, which would still close the issue on merge). A second closing path is also plugged: the squash commit subject comes from the PR title (`feat: {title}`), so a card titled `fix: #6.3 address review` made GitHub read `#6` as a closing reference. PR titles now neutralise any `#n` that follows a closing keyword or a conventional-commit prefix and is not the card's own clean source-issue reference (`fix: #6.3` → `fix: 6.3`). Cross-repo source issues still get `Refs <full-url>` as before.
